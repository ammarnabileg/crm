## What needs review
- **P4 live provider adapters are intentionally deferred.** The provider contract,
  guard, optimizer, router, fallback and audit are complete and tested offline via
  `FakeProvider`. Real HTTP adapters (OpenAI/Claude/…) need live tenant keys +
  network to verify, so per DW-15 they are a runtime integration step, not part of
  the tested core. They plug into the gateway's registry without changing it.
- **No builder/runtime UI yet** for P3 (backend-first per roadmap); a visual editor
  is a later UI phase. RBAC permissions (`workflows.manage`, `ai.manage`) ship with
  their controllers so none dangles.

## Current risks
- **Low — workflow cycles.** The runtime has a `max_steps` guard; authors can still
  build long graphs. Validation guarantees reachability + structural soundness, not
  acyclicity (cycles are sometimes legitimate, e.g. follow-up loops).
- **Low — guard tuning.** PromptGuard thresholds/patterns are conservative; real
  candidate phrasing should be monitored so legitimate answers are never blocked
  (current default hardens rather than blocks below the threshold).

## Future risks
- **Live-model phases (P5+).** The Orchestrator and agents will drive real calls
  through the `AiGateway`; their *logic* is testable with `FakeProvider`, but output
  *quality* needs live keys. Plan a sandbox/benchmark pass (P9) once a test key exists.
